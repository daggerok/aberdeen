GENERIC PLAN — how to build a new brand's ETF-holdings-to-watchlist app
so it looks, behaves, and is built exactly like the other 14 sibling repos.
=============================================================================

MANDATORY WORKLOG AND RECOVERY PROTOCOL
=======================================
Use the repository-root .worklog.txt as the canonical, self-contained handoff
file. This is a workflow requirement, not permission to change product scope.

1. BEFORE WORK
   If .worklog.txt exists, read it completely before changing code. Check the
   actual working tree, branch, local/remote commits and PR states; the file
   may be stale after a crash or external changes. Read long files in chunks;
   do not treat truncated tool output as a complete read. Resume the first unfinished
   step, not the whole implementation. Preserve existing user changes.
   If the file does not exist, create it before implementation. Include the
   full original text of all supplied plans/specifications, sanitized of
   secrets, plus relevant user amendments and their precedence. A link to a
   plan or a statement that it was read is not a substitute for its text.
   Preserve existing plan.txt and .plans history during migration. Embed their
   full relevant text/JSON content so recovery does not depend on old chat,
   temporary files, .git scratch directories or an agent's memory.

2. REQUIRED CONTENT
   Keep a concise CURRENT STATE at the top: goals/acceptance criteria; hard
   constraints; exact authorization scope for edits, pushes, PRs and merges;
   repository/branch/PR identifiers; completed, active and remaining work;
   last confirmed pushed SHA; blockers; and the exact next command or action.
   Below it keep an append-only factual journal of decisions, brief reasons,
   actions, changed paths, commands, test/build results, failures and fixes,
   useful source URLs with findings, unresolved assumptions and recovery
   instructions. Record expected versus actual results, including known
   baseline failures. Distinguish planned, attempted, completed and verified.
   Include full original inputs and up-to-date text snapshots of relevant
   .plans files, manifests and rollout ledgers, with clear section boundaries.
   For large/binary evidence, keep a tracked artifact and its path/hash plus
   enough facts in the log to resume; do not pretend it is embedded text.
   Record factual conclusions and short decision rationales, not private
   chain-of-thought or a transcript of every internal consideration.

3. CHECKPOINT CADENCE
   After every small, meaningful completed step (a research finding, decision,
   bounded code change, validation or publication), update .worklog.txt and
   make a scoped Conventional Commit on the feature branch; push it before
   starting the next step. For research-only progress, commit the log alone.
   Do not accumulate an entire session before the first checkpoint. Do not
   create empty commits or commit secrets, caches, dependencies or build output.
   Test coherent code changes before publishing; if work must stop while
   incomplete, label the checkpoint WIP and state exactly what fails/remains.
   Verify pushes against the remote. Record the last confirmed pushed SHA in
   the next checkpoint; do not claim the current commit was pushed before it
   succeeds. The commit containing the log is also identifiable via git log.
   If push/auth/network fails, keep a local checkpoint and record the exact
   unpushed state and safe recovery steps; never invent successful publication.

4. INTERRUPTION SAFETY
   Checkpoint continuously: a final message or graceful shutdown is not
   guaranteed before context/rate/time limits. Before a foreseeable stop,
   refresh CURRENT STATE with the next action, ongoing processes, checkpoints,
   blockers and validation still needed. No essential recovery information
   should exist only in chat, process memory or disposable workspace files.
   Report unexpected scope uncertainty instead of inventing requirements.

5. SAFETY AND AUTHORIZATION
   Never store credentials, PATs, auth headers, cookies or sensitive environment
   values in logs, source files, URLs, commits or copied original inputs.
   Use runtime-only authentication and note only whether access is available.
   Work on feature branches; never force-push, overwrite concurrent changes,
   bypass checks/protections, or merge without explicit authorization for that
   repository and change. Existing scoped authorization need not be asked for
   again. An old README-only permission is not general code-merge permission.

RESTART PROMPT
Read .worklog.txt completely first. Verify its CURRENT STATE against the actual
working tree, branch, remote commits and PRs. Tell me briefly what is complete,
what remains and any mismatch. Continue from the first unfinished step within
the recorded authorization, without repeating completed work. After each small
meaningful step, update .worklog.txt, commit and push as specified above.

THE #1 RULE, READ THIS BEFORE ANYTHING ELSE:
THE WEB APP (index.html + app.tsx) IS THE SAME APP EVERYWHERE.
IT IS NOT "INSPIRED BY" A SIBLING. IT IS A COPY OF ONE, WITH A SMALL,
FIXED, ENUMERATED SET OF STRINGS SUBSTITUTED. NOTHING ELSE CHANGES.
=============================================================================
This was violated the first time this plan was used (Global X,
init-global-x branch) — the resulting app.tsx invented new tooltip wording
per column, added whole new fund-detail rows/sections (a "Documents" block
with Prospectus/SAI/Annual Report links, "Management Fee", "NAV Daily
Change", extra Distribution fields, etc.) that don't exist in the sibling
it was supposedly based on. That is exactly the failure mode this section
exists to prevent. Diffing two siblings' app.tsx against each other (e.g.
daggerok/JPMorgan vs daggerok/Schwab — check this yourself, it's cheap)
shows they differ in EXACTLY these things and nothing else:
  1. The file-header comment (`@file <Brand> Watchlist Application`)
  2. The localStorage key prefixes (THEME_KEY, SELECTED_KEY,
     BLACKLIST_KEY, ACTIVE_FUND_KEY, FILTERS_KEY, LEGACY_FILTERS_KEY,
     SORTS_KEY, SITE_STATE_KEY — each is `'<brand-lowercase>-<suffix>'`)
  3. INDEX_URL (`./api/<brand>/index.json`) and every other literal
     `api/<brand>/...` path string
  4. The export filename prefix (`<brand>-${scope}-${stamp}.${ext}`)
  5. Human-facing status/subtitle strings that name the brand or the
     source site by name, e.g. "Search <Brand> ETFs, select ETFs via the
     'Use' checkbox…", "Loading <Brand> ETF data from…", "Data:
     api/<brand>/index.json generated from <a href=official-site-url>the
     official <source description>…</a> + SEC EDGAR N-PORT-P (<Trust
     name>, CIK <number> — holdings fallback only) + Yahoo Finance…"
     Mandatory shared Frequency display rule (also applies when the source
     sibling still uses the old label): in formatDividendFrequency(),
     replace the fallback display string "00 - —" with "00 - None".
     Null, undefined, empty/whitespace-only values and the existing dash
     placeholders must display "00 - None". Keep explicit "Unknown" as
     "00 - Unknown" and all other frequency labels/mappings unchanged.
     This is presentation only: "None" here is the requested placeholder,
     not evidence that a fund never pays distributions. Do not change
     provider data, API values/schema, dividend inference, sorting logic,
     UI structure or exports; existing consumers of the formatted value
     must receive the corrected label. Record this exact string-only
     correction in the UI parity substitutions and add regression tests.
  6. The column-help tooltip TEXT STRINGS (the `columnHelp`/help-text
     object) — ONLY to the extent the underlying field's PROVENANCE
     sentence names a different source site/company (e.g. "as published
     by am.jpmorgan.com" -> "as published on the official <Brand> fund
     page"). The KEY SET of that object (which columns have a tooltip at
     all), the STRUCTURE of each sentence, and the ORDER never change.
     Do not add adjectives, extra caveats, or extra detail sentences that
     a sibling's version doesn't have for the equivalent field, even if
     the brand's real site happens to publish something extra — see the
     next point.
  7. The fund-detail-view ROWS list (whatever variable builds the
     "Fund"/"Cost"/"Price"/"Assets"/"Returns"/"Distributions"/"Holdings"
     sections in the per-fund overview tab): the EXACT SAME set of
     `{ section, metric, value }` rows in the EXACT SAME order as the
     sibling you copied from, with `value` computed from THIS brand's own
     `meta`/`fund` fields — but if a row's value simply isn't available
     for this brand, show it as null/blank (which the existing rendering
     already collapses/hides), do NOT delete the row, rename the metric,
     or add a brand-specific new row for data the sibling's version
     doesn't surface, even if the official site happens to publish more.
     If a brand's site truly publishes something no sibling captures at
     all (e.g. a document library), that is a candidate for extending
     update-data.ts's meta.json schema project-wide (all 15+ brands get
     the new field's plumbing, even if most show it blank) — it is NOT
     grounds for a one-off app.tsx addition. Flag it in your report
     instead of adding it unilaterally.
  8. The SEC EDGAR Trust name / CIK / provider name baked into user-facing
     copy (point 5's "<Trust name>, CIK <number>").

Explicit user-approved type-safety exception (TS2345): if withTickerChain<T>
stores work.catch(() => undefined) in Map<string, Promise<void>>, replace that
expression with work.then(() => undefined, () => undefined). Keep returning
work to preserve the caller's Promise<T> value/rejection. Do not weaken the
map type or suppress diagnostics. Record the exact line in the UI parity
substitutions and test queue serialization and recovery after rejection.

Apart from the explicit corrective exceptions above, THAT IS THE COMPLETE
LIST. If a change you're about to make to app.tsx or
index.html isn't one of these 8 substitution categories, don't make it —
copy the sibling's code for that part verbatim instead, byte for byte,
including comments. This specifically means: do NOT rewrite tooltip
prose "to be more accurate/detailed for this brand", do NOT add rows,
sections, columns, icons, colors, or layout tweaks, do NOT reorder
anything, do NOT change how row selection, search, filters, sort,
watchlist, blacklist, CSV/TXT export, or dark mode work. The user's own
words: "our whole web app should be exactly similar to other apps, only
the way we get data is different, so different will be only data it
renders."

Practical workflow: `cp` (or `git show <sibling>:app.tsx >`) the sibling's
app.tsx and index.html into the new repo first, THEN make ONLY the 8
substitutions above with find/replace, THEN diff your result against the
sibling one more time before considering the UI done — the diff should be
short and every hunk should map to one of the 8 categories. If your diff
is long or touches component logic/JSX structure, you did it wrong; revert
and start over from the copy.

4. scripts/update-data.ts — STRUCTURE (copy this shape from
   daggerok/JPMorgan as the primary reference; it currently has every fix
   from this project's history applied correctly)
-----------------------------------------------------------------------------
A. Shared "output helpers" prelude (copy near-verbatim from JPMorgan
   scripts/update-data.ts lines 1-~130; every sibling has an identical or
   near-identical copy of this block — it's the same in Vanguard, Schwab,
   WisdomTree, etc. too if you want a second reference point):
     - outputClean(value) — stringify, strip control chars
     - outputVerbose() / outputNote(message) — VERBOSE env gate; anything
       printed via outputNote is a per-fund/per-request retry or fallback
       notice, hidden unless VERBOSE=1
     - outputConfigEntries(config) — turns the config object into
       [ENV_NAME, value] pairs for the header (MAX_FETCHES/REQUEST_SLEEP/
       CONCURRENCY sort first, everything else alphabetical)
     - outputPrintConfig(brand, config) — prints:
         [ config   ] <Brand> updater:
                       MAX_FETCHES=...
                       ...
                       VERBOSE=false
       Label is padded to 9 chars inside the brackets: `[ ${label.padEnd(9)}] `.
       ALL bracket-style status lines in the file use this exact 9-wide
       padding — config, filter, catalog, cursor, done, edgar, product,
       holdings, history, chart, retry, etc. Keep them consistent.
     - outputPrintFilter(selected, total, deferred?) — prints
       `[ filter   ] N of M funds pass filters` (or "selected for
       evaluation (data-dependent filters applied per fund)" if some
       filters can only be checked after fetching a fund's own page)
     - outputStable(value) / outputContentKey(value) — deep-sorts an
       object's keys and strips `generatedAt`/`catalogReadAt` recursively,
       so the console's before/after digest comparison ignores run
       timestamps. (Note: this only affects the CONSOLE status label. The
       actual file WRITE needs its own protection — see section 5.)
     - outputInspectFund / outputCreateReporter — hashes a fund's on-disk
       files before and after processing to decide "updated" vs
       "unchanged" for the console line, independent of whatever status
       string the business logic passes in.
     - outputCount(value), outputScalar(value), outputMoney(value) —
       formatting helpers for the per-fund line.
     - outputFundLine(index, total, ticker, status, data, reason) —
       builds ONE line per fund:
         [  8/81  ] TICK  updated   history=1234 holdings=56 divs=7
                    netAssets=$1.2B div=4.5 sec=4.9 reason=...
       Fields that are null/undefined/'null' are OMITTED entirely (not
       printed as `field=null`) — real 0 and false values ARE printed.
       This is the single most important formatting rule the whole
       project converged on this year: never print `port=null` or
       `(official=null yahoo=null)`.

B. UpdaterConfig + env parsing (copy shape from JPMorgan or Invesco):
     - envValue(env, name, aliases[]) reading process.env
     - parsePositiveInt / parseDecimal / parseAumBound / parseRanges for
       MIN:MAX-style filters (AUM, TER, DIVIDEND_YIELD, SEC_YIELD,
       PERFORMANCE_{YTD,1Y,3Y,5Y,10Y}, TOTAL_RETURN_{YTD,1Y,3Y,5Y,10Y})
     - AUM presets: nano <$10M, micro $10M-$300M, small $300M-$2B,
       mid $2B-$10B, large >=$10B
     - MAX_FETCHES / CONCURRENCY / REQUEST_SLEEP / MAX_RETRIES / TICKERS
     - printHelp()/-h/--help support mirroring every env var

C. Request pacing — CONCURRENCY workers, each with its OWN paced lane.
   Do NOT use a single shared gate (`let nextRequestAt = 0` compared/
   updated by every caller) — that was a real bug fixed across 10 of the
   14 repos this year: it caps total throughput at one request per
   REQUEST_SLEEP no matter how high CONCURRENCY is set, because all
   workers share the same timer. Copy the FIXED pattern from
   daggerok/WisdomTree or daggerok/iShares scripts/update-data.ts
   (`paceRequests`/`createRequestGate`): an array of N independent lane
   timestamps sized from config.concurrency, each call picks the
   least-recently-used lane, computes wait FROM that lane, sleeps, then
   writes the new timestamp to THAT SAME lane (not a freshly re-scanned
   one — that was a subtle bug caught in code review, see the exact
   working implementation, don't re-derive it from scratch).
   EXCEPTION: if this brand's site turns out to be WAF-protected (see
   section 6), keep it as a SINGLE shared, conservative gate instead —
   speeding up direct requests to a site that's actively fingerprinting/
   blocking you is the wrong tradeoff. Franklin and Goldman-Sachs were
   deliberately left on the single-gate pattern for exactly this reason.

D. Fallback chain (standard across all 14):
     official site (whatever this brand's plan says) for catalog + the
       fund's own headline fields
     -> SEC EDGAR N-PORT-P for holdings, if the official site doesn't
        publish full holdings or a per-fund page fetch fails. Reuse the
        N-PORT parsing helpers verbatim from JPMorgan (loadFundTickerTable,
        loadCompanyTickerTable, resolveNportFiling, parseNport,
        parseCompanyTickerMap, secHeaders) — this code is duplicated
        near-identically across ~8 sibling repos, it's safe to copy as-is.
     -> Yahoo Finance chart API (query1.finance.yahoo.com/v8/finance/chart)
        for price/NAV history and dividends when the official site doesn't
        provide enough history, or as the sole history source if the
        brand's own site has none.
     -> previous published data (read the existing committed meta.json/
        holdings/history) as the last resort, so a run that can't reach a
        source never deletes/blanks data that was already published.

   Yahoo's adjusted-close is recomputed on every request and jitters in
   the last digit or two between otherwise-identical requests. Round it
   to 2 decimals wherever it's parsed or written (real fix applied broadly
   this year) — otherwise every fund looks "updated" on every run forever.
   See JPMorgan's chart-parsing function for the exact `round(adjClose, 2)`
   placement.
   Also: never store the LIVE fetch URL (with period1/period2 query
   params reflecting "now") as a persisted "source" field — build a
   separate, stable, query-string-free URL for that. Same reasoning:
   otherwise that field alone makes the file diff every run.

E. Output-changed detection ("idempotency"): after building the final
   value to write, do NOT just byte-compare it against the on-disk file
   if it embeds anything timestamp-like (generatedAt, catalogReadAt, or
   similar). Two equally-valid patterns exist in the sibling repos, pick
   either:
     (a) writeJsonIfChanged() that strips generatedAt/catalogReadAt
         RECURSIVELY (they can be nested, e.g. under a `source` object —
         a shallow top-level-only strip was a real bug found and fixed in
         ProShares) before comparing, and only writes with the fresh
         object (fresh timestamp included) if something else differs. See
         daggerok/JPMorgan's samePublishedContent + the write call site,
         or daggerok/ProShares's writeJsonIfChanged (the recursive one).
     (b) build the candidate object with the PREVIOUS run's timestamp,
         write-if-changed, and only if that resulted in an actual write,
         re-write once more with a fresh timestamp. See daggerok/VanEck or
         daggerok/Neos's index-writing code for this variant.
   Whichever you pick, apply it to every file that embeds a run timestamp
   — typically both the top-level index.json AND each fund's own
   meta.json if it also carries one.

F. Per-fund processing: continue-on-error, not fail-fast. One fund's
   fetch failing must not abort the whole run — catch it, report
   'failed' on that fund's line via output.result(...), keep its
   previously-published data, move on to the next fund. See any sibling's
   worker loop (e.g. JPMorgan's `worker()` function or iShares'
   mapWithConcurrency usage) — none of the current 14 rethrow out of a
   per-fund catch block, and that's intentional.

G. Console output contract (do not deviate):
     [ config   ] <Brand> updater:
                   <ENV_NAME>=<value>
                   ...
                   VERBOSE=false
     [ catalog  ] <N> <Brand> ETFs (<source description>)      (optional,
                                    only if there's a discovery/catalog step)
     [ filter   ] <N> of <M> funds pass filters
     [  1/N   ] TICK  updated   history=123 holdings=45 divs=6 netAssets=$1.2B ...
     ...
     [ done     ] <N> funds updated, <M> failures
     [ done     ] counts: ...
   Every fund line comes from outputFundLine via outputCreateReporter, in
   the same call shape as every sibling. Do not hand-roll a different
   per-fund line format.

6. WAF / anti-bot handling (only if section 1's live check found this)
-----------------------------------------------------------------------------
Copy the proxy-fallback approach from daggerok/Franklin or daggerok/Schwab
scripts/update-data.ts: try a direct fetch with a normal browser User-Agent
first; after a small number of consecutive denials
(ISSUER_DIRECT_DENIAL_LIMIT-style counter), switch to routing the same URL
through a read-only rendering proxy (r.jina.ai) for the rest of the run,
and print one `[ issuer  ]`-style notice (always visible, not behind
VERBOSE) when that switch happens. Keep REQUEST_SLEEP conservative and do
NOT apply the per-worker-lane speedup from section 4C to the direct-fetch
path in this case.

7. .github/workflows/update-data.yml
-----------------------------------------------------------------------------
Copy from daggerok/JPMorgan (or any sibling — this file was standardized
across all 14 this year):
  on:
    schedule:
      - cron: '0 0 * * 0'   # every Sunday 00:00 UTC — confirmed against
                              # GitHub's own docs, day-of-week 0 = Sunday
    workflow_dispatch:
      inputs: <one input per ENV var the updater reads, mirrored 1:1,
               same names/defaults as the config header prints>
  jobs:
    update-data:
      steps:
        - name: Checkout
          uses: actions/checkout@v7      # check current major, Dependabot
                                          # keeps this current — don't pin
                                          # an old major on purpose
        - name: Setup bun
          uses: oven-sh/setup-bun@v2
          with: {bun-version: latest}
        - name: Install dependencies
          run: bun install --frozen-lockfile
        - name: Run updater unit tests
          run: bun test scripts/update-data.test.ts
        - name: Generate api/<brand> static data
          run: bun ./scripts/update-data.ts
          env: <map every workflow_dispatch input to the matching ENV var>
        - name: Commit updated data
          run: |
            <git config, git add api/<brand>, commit if diff, push>
Do NOT add a `bunx tsc` type-check step — see section 3. Do NOT add a
`push:` trigger that re-runs on every commit to update-data.ts — schedule
+ manual dispatch only (a push-triggered auto-refresh on every merge was a
real bug found and fixed in Franklin this year).
